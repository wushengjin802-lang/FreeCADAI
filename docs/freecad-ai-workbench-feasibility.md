# FreeCAD AI 智能工作台可行性评估与实施路线

## 1. 目标概述

本项目目标是在本机已安装 FreeCAD 绘制工具的基础上，开发一个集成 LLM API 的专属 AI 智能工作台。用户可以在 FreeCAD 内通过文本或语音描述建模需求，插件在后台调用大模型生成可执行的 FreeCAD Python 脚本，并在当前 FreeCAD 视图中直接创建和渲染 3D 模型。

长期目标是演进为 SaaS 平台服务，提供用户账号、模型任务管理、云端推理、模型资产库、团队协作、计费和企业化部署能力。初期建议以 FreeCAD 插件形态落地，验证自然语言建模、脚本生成、执行安全、交互闭环和用户价值。

## 2. 结论摘要

整体可行，且适合先做插件 MVP。

FreeCAD 原生支持 Python 脚本、Workbench 扩展、宏命令、自定义面板和 3D 视图操作，因此非常适合作为 AI 建模插件的宿主。LLM 负责将用户意图转换为 FreeCAD Python 脚本，插件负责 UI、上下文采集、脚本审查、执行、结果渲染和错误反馈。

核心难点不在于“能否生成模型”，而在于：

- 如何让 LLM 稳定生成可执行、可维护、可解释的 FreeCAD Python 脚本。
- 如何限制脚本权限，避免任意文件、网络、系统命令等安全风险。
- 如何在失败时自动回传错误并迭代修复，而不是让用户面对 Python 报错。
- 如何把“对话生成模型”变成可靠的工程工作流，包括参数化、版本管理、模型编辑和导出。
- 如何从本地插件自然演进到 SaaS，而不是一开始就过度平台化。

建议路线：先构建本地 FreeCAD 插件 MVP，接入一个 LLM API，支持文本输入、脚本生成、预检查、执行、渲染和错误修复；第二阶段加入语音、参数化控件、脚本模板库和历史记录；第三阶段再拆出云端服务，形成 SaaS 架构。

## 3. 推荐产品形态

### 3.1 初期形态：FreeCAD 插件

初期产品应是一个 FreeCAD 内部 Workbench 或 Dockable Panel，提供独立 UI，不侵入 FreeCAD 原有界面。

建议功能：

- 文本输入：用户输入“创建一个带四个安装孔的法兰盘”等自然语言。
- 语音输入：录音后转写为文本，再进入同一建模流程。
- 任务面板：显示当前提示词、生成状态、脚本预览、执行结果和错误信息。
- 当前场景上下文：读取当前文档对象、选择对象、单位、视角、已有几何体名称。
- LLM 调用：把用户需求和上下文发送给大模型。
- 脚本生成：要求模型输出受限 FreeCAD Python 代码。
- 安全检查：在执行前拦截危险 API 和不符合约束的代码。
- 模型渲染：在当前 FreeCAD 文档中执行脚本并刷新视图。
- 自动修复：执行失败时，把错误栈、对象状态和原脚本回传给 LLM 生成修正版。
- 历史记录：保留每次 prompt、脚本、结果和模型版本。

### 3.2 中期形态：本地插件 + 云端 API

中期可以把 LLM 调用、用户账号、任务历史、模板库、额度控制迁移到后端服务。

本地插件只负责：

- FreeCAD UI。
- 当前文档上下文采集。
- 脚本执行。
- 3D 结果展示。
- 本地文件导入导出。

云端服务负责：

- LLM API 编排。
- 用户认证和授权。
- Prompt 模板管理。
- 任务队列和日志。
- 计费、额度和风控。
- 模型生成质量评估。

### 3.3 长期形态：SaaS 平台

长期 SaaS 可以支持：

- Web 端项目管理和模型资产库。
- FreeCAD 插件登录同一账号同步项目。
- 团队协作、共享模板、企业私有知识库。
- 云端批量生成、仿真、渲染或格式转换。
- 插件市场或行业模板库，例如机械零件、夹具、建筑构件、家具、机器人结构件。
- 私有化部署或企业专属模型网关。

## 4. 技术可行性分析

### 4.1 FreeCAD 插件能力

FreeCAD 适合作为 AI 工作台宿主，原因如下：

- FreeCAD 本身大量能力通过 Python 暴露，包括建模、文档对象、Part、Sketcher、Draft、TechDraw 等模块。
- 可以开发自定义 Workbench，提供菜单、工具栏、命令和停靠面板。
- 可以通过 PySide/PySide2 构建 Qt UI，与 FreeCAD 主界面风格一致。
- Python 脚本可直接创建几何对象并刷新当前 3D 视图。
- 可读取当前文档、选择集、对象属性，为 LLM 提供上下文。
- 可导出 STEP、STL、OBJ、FCStd 等文件，方便后续 SaaS 资产管理。

技术判断：插件开发可行，是最短路径。

### 4.2 LLM 生成 FreeCAD Python 脚本

LLM 可以生成 FreeCAD Python 脚本，但需要通过工程约束提高稳定性：

- 使用固定 system prompt，明确只允许输出 Python 脚本或结构化 JSON。
- 提供 FreeCAD API 使用规范和少量高质量示例。
- 要求模型优先生成参数化、可读、分步骤的代码。
- 使用 JSON schema 约束输出，例如 `explanation`、`script`、`parameters`、`expected_objects`。
- 插件侧做代码静态检查，禁止危险模块和危险调用。
- 失败后自动把错误信息回传给 LLM 修复。

技术判断：可以实现，但必须把 LLM 当成“代码生成器 + 迭代修复器”，不能直接无约束执行模型输出。

### 4.3 UI 隔离

建议使用 FreeCAD Dock Widget 方式构建良好隔离的 AI 面板：

- 左侧或右侧停靠，不覆盖建模视图。
- 插件 UI 自成体系，包括输入区、执行按钮、语音按钮、脚本区、历史区。
- 不修改 FreeCAD 核心 UI，不替换原有工具栏。
- 插件配置、缓存、日志放在独立目录。

推荐 UI 模块：

- `PromptPanel`：文本输入和语音输入。
- `GenerationStatus`：展示调用中、生成中、检查中、执行中。
- `ScriptPreview`：展示生成脚本，允许高级用户查看和复制。
- `ResultPanel`：展示创建对象、耗时、错误和修复建议。
- `HistoryPanel`：列出历史生成记录。
- `SettingsPanel`：配置 API Key、模型、服务地址、安全策略。

### 4.4 语音输入

语音不是 MVP 必需项，但可以在第二阶段加入。实现方式有两种：

- 本地录音 + 云端语音识别 API。
- 本地录音 + 本地 Whisper 类模型转写。

建议先实现文本输入，把语音作为同一 prompt 管线的输入来源。语音识别结果应该允许用户确认或编辑，避免误识别直接触发建模。

### 4.5 安全性

这是项目成败的核心之一。LLM 生成 Python 后，如果直接在 FreeCAD 进程中执行，理论上可以访问本机文件、网络和系统命令，风险较高。

初期至少需要做以下限制：

- 禁止导入危险模块：`os`、`sys`、`subprocess`、`socket`、`shutil`、`pathlib`、`requests` 等。
- 禁止文件写入、删除、网络访问、进程启动。
- 脚本执行前做 AST 静态检查。
- 只允许调用白名单 FreeCAD API。
- 提供执行前预览和用户确认开关。
- 所有脚本保留日志，方便追溯。
- 异常时捕获并阻止连续执行。

更稳妥的中期方案：

- 将代码生成与代码执行分离。
- 使用受控执行器运行脚本。
- 采用白名单 DSL 或命令 JSON，而不是直接执行任意 Python。

长期 SaaS 场景中，应尽量让 LLM 输出结构化建模指令，再由本地插件解释执行。例如：

```json
{
  "operations": [
    {
      "type": "box",
      "name": "base",
      "width": 100,
      "depth": 60,
      "height": 12
    },
    {
      "type": "cylinder_cut",
      "target": "base",
      "diameter": 8,
      "positions": [[15, 15], [85, 15], [15, 45], [85, 45]]
    }
  ]
}
```

这样可以显著降低任意代码执行风险。

## 5. 建议架构

### 5.1 插件 MVP 架构

```text
User
  |
  v
FreeCAD AI Dock Panel
  |
  +-- Text / Voice Input
  +-- Context Collector
  +-- Prompt Builder
  +-- LLM Client
  +-- Script Validator
  +-- Script Executor
  +-- Result Renderer
  +-- Error Repair Loop
  |
  v
Current FreeCAD Document / 3D View
```

### 5.2 模块划分

建议插件目录结构：

```text
FreeCADAI/
  Init.py
  InitGui.py
  package.xml
  freecad_ai/
    __init__.py
    workbench.py
    commands.py
    ui/
      ai_panel.py
      settings_panel.py
      history_panel.py
    llm/
      client.py
      prompts.py
      schemas.py
    freecad/
      context.py
      executor.py
      validator.py
      renderer.py
    speech/
      recorder.py
      transcriber.py
    storage/
      config.py
      history.py
    resources/
      icons/
```

### 5.3 调用流程

```text
1. 用户输入建模需求
2. 插件采集当前 FreeCAD 文档上下文
3. Prompt Builder 组合系统约束、用户需求、上下文、输出格式
4. LLM 返回结构化结果和 Python 脚本
5. Script Validator 做静态检查和白名单检查
6. 用户确认执行，或在开发模式下自动执行
7. Script Executor 在 FreeCAD 当前文档中运行脚本
8. 渲染 3D 模型并刷新视图
9. 如果失败，收集错误信息并触发修复循环
10. 保存任务历史
```

## 6. MVP 功能范围

第一版建议聚焦“文本生成 3D 模型”，不要同时做太多平台能力。

### 6.1 必做

- FreeCAD 插件安装和加载。
- 独立 AI Dock Panel。
- API Key 和模型配置。
- 文本输入。
- 当前文档上下文采集。
- LLM 生成 FreeCAD Python 脚本。
- 脚本预览。
- 基础安全校验。
- 一键执行并渲染模型。
- 错误捕获和一次自动修复。
- 本地历史记录。

### 6.2 可选

- 语音输入。
- 多轮对话修改模型。
- 参数自动识别和表单化。
- 常见零件模板库。
- STEP/STL 导出快捷按钮。
- 截图或视图快照。

### 6.3 暂不建议第一版做

- 完整 SaaS 后台。
- 团队协作。
- 复杂权限系统。
- 云端几何建模执行。
- 多 CAD 软件适配。
- 企业知识库。
- 计费系统。

## 7. 阶段计划

### 阶段 0：环境验证

目标：确认本机 FreeCAD 插件开发链路可用。

任务：

- 确认 FreeCAD 版本、Python 版本、PySide 版本。
- 创建最小 Workbench 或 Macro。
- 在 FreeCAD 内显示一个 Dock Panel。
- 运行一段固定 Python 脚本生成立方体或圆柱。
- 验证插件安装路径和启动方式。

验收标准：

- FreeCAD 启动后能看到 AI 工作台或 AI 面板。
- 点击按钮能在当前文档生成一个简单 3D 对象。

### 阶段 1：文本到脚本 MVP

目标：用户输入文字，插件调用 LLM 生成模型。

任务：

- 实现插件 UI。
- 实现 LLM API Client。
- 设计 prompt 模板和输出 JSON schema。
- 实现脚本预览。
- 实现基础安全校验。
- 执行生成脚本并刷新视图。
- 记录 prompt、脚本、结果。

验收标准：

- 输入“生成一个长 100、宽 60、高 10 的底板，四角有孔”，能生成基本模型。
- 失败时显示错误，不导致 FreeCAD 崩溃。
- 历史记录可查看。

### 阶段 2：错误修复与建模质量提升

目标：提升脚本成功率和用户体验。

任务：

- 把执行错误、FreeCAD 对象状态、原始脚本回传给 LLM。
- 支持自动修复 1 到 3 次。
- 增加常见建模模板示例。
- 增加参数化输出，例如尺寸、孔径、数量。
- 增加“修改当前模型”的上下文能力。
- 支持选择对象后进行局部修改。

验收标准：

- 常见机械零件生成成功率明显提升。
- 用户可以说“把孔径改成 10mm”并更新模型。
- 失败任务能给出可理解的原因。

### 阶段 3：语音输入与体验增强

目标：让用户可以用语音驱动同一建模流程。

任务：

- 实现录音按钮。
- 接入语音识别。
- 展示转写文本并允许编辑。
- 转写确认后进入已有文本生成流程。
- 增加任务状态和取消按钮。

验收标准：

- 用户语音描述后可生成文本 prompt。
- 用户确认后可生成模型。
- 误识别不会直接执行危险操作。

### 阶段 4：云端服务拆分

目标：把可 SaaS 化的部分从插件中拆到后端。

任务：

- 设计后端 API：生成、修复、历史、模板、用户配置。
- 增加用户账号和 token。
- 插件登录云端服务。
- 后端管理 prompt 模板和模型路由。
- 记录任务日志和生成质量数据。
- 支持额度控制。

验收标准：

- 插件不再直接保存 LLM API Key。
- 用户任务可以同步到云端。
- 后端可以按用户、项目、模型统计调用。

### 阶段 5：SaaS 平台

目标：形成可商业化服务。

任务：

- Web 控制台。
- 项目和模型资产管理。
- 模板市场。
- 团队协作。
- 计费和套餐。
- 企业私有部署选项。
- 插件自动更新机制。

验收标准：

- 用户可以注册、登录、管理项目和额度。
- FreeCAD 插件与 SaaS 账号互通。
- 平台具备基本商业闭环。

## 8. 关键技术风险与应对

| 风险 | 影响 | 应对策略 |
| --- | --- | --- |
| LLM 生成脚本不可执行 | 用户体验差 | 使用 schema、示例、自动修复、测试集 |
| 任意 Python 执行风险 | 高安全风险 | AST 检查、API 白名单、用户确认、逐步转 DSL |
| FreeCAD API 差异 | 跨版本不稳定 | 明确支持版本，做兼容层 |
| 复杂模型生成质量不稳定 | 难商业化 | 先聚焦高频零件和模板化场景 |
| 语音误识别 | 误操作 | 语音只生成文本，执行前确认 |
| 插件崩溃影响 FreeCAD | 用户丢工作 | 捕获异常、自动保存、隔离日志 |
| SaaS 太早投入过大 | 研发成本失控 | 先用插件验证需求，再平台化 |

## 9. 推荐技术选型

### 插件侧

- 语言：Python。
- UI：PySide/PySide2，跟随 FreeCAD 当前环境。
- 插件形态：FreeCAD Workbench + Dock Widget。
- 本地存储：JSON 或 SQLite。
- 脚本校验：Python `ast` 模块 + 自定义白名单。
- 日志：本地 rotating log。

### LLM 侧

- 初期：直接接入一个主流 LLM API。
- 输出：优先 JSON schema，脚本字段单独承载。
- Prompt：系统约束 + FreeCAD API 示例 + 当前上下文 + 用户需求。
- 修复：基于错误栈和原脚本做 repair prompt。

### SaaS 侧

- 后端：FastAPI 或 Node.js/NestJS。
- 数据库：PostgreSQL。
- 队列：Redis + worker。
- 对象存储：保存模型文件、截图、任务附件。
- 认证：JWT/OAuth。
- 部署：Docker + 云主机或 Kubernetes。

## 10. 建议的第一版 Prompt 输出协议

建议要求 LLM 返回如下 JSON：

```json
{
  "summary": "创建一个带四个安装孔的矩形底板",
  "parameters": {
    "length": 100,
    "width": 60,
    "height": 10,
    "hole_diameter": 8
  },
  "script": "import FreeCAD as App\nimport Part\n...",
  "expected_objects": ["BasePlate"],
  "notes": ["单位为 mm"]
}
```

插件只读取 `script` 字段，并在执行前做校验。不要让模型返回散乱 Markdown 后再用字符串截取代码块。

## 11. 商业化路径

建议从垂直场景切入，而不是泛化为“什么 CAD 都能做”。

可选切入方向：

- 机械零件快速建模。
- 夹具、治具和工装设计。
- 3D 打印零件生成。
- 教育场景：自然语言学习 CAD。
- 建筑或家具的参数化原型。
- 企业内部标准件库生成。

早期商业价值可以来自：

- 提高设计初稿速度。
- 降低 FreeCAD 学习门槛。
- 复用企业标准件模板。
- 把自然语言需求转换为可编辑参数化模型。

SaaS 计费可按：

- 月度订阅。
- 生成次数。
- 团队席位。
- 企业私有化部署。
- 行业模板库授权。

## 12. 推荐下一步

建议立即开始阶段 0 和阶段 1。

第一周目标：

- 搭建 FreeCAD 插件骨架。
- 在 FreeCAD 中显示 AI Dock Panel。
- 输入固定文本后调用一个 mock LLM 或固定脚本。
- 点击按钮生成简单模型。

第二周目标：

- 接入真实 LLM API。
- 实现 JSON 输出协议。
- 实现脚本预览和 AST 安全检查。
- 支持 3 到 5 个典型建模 prompt。

第三到四周目标：

- 加入错误修复循环。
- 加入历史记录。
- 提升典型 prompt 成功率。
- 准备演示用案例。

## 13. 最小演示案例

建议 MVP 至少覆盖以下 5 个演示：

1. 创建一个指定尺寸的长方体底座。
2. 创建一个带四个安装孔的法兰或底板。
3. 创建一个圆柱、倒角或简单轴类零件。
4. 基于当前对象执行“加孔”“改尺寸”“移动位置”等修改。
5. 生成失败后自动修复一次并成功渲染。

## 14. 最终判断

该项目作为 FreeCAD 插件启动非常可行，技术路径清晰，MVP 成本可控。真正需要重点投入的是脚本安全、生成稳定性、错误修复闭环和场景聚焦。

建议不要一开始就做完整 SaaS，而是先用插件验证自然语言建模体验和高频行业场景。只要插件阶段能证明用户愿意反复使用、生成结果可控、失败可修复，再拆分云端服务并进入 SaaS 化，会更稳。
